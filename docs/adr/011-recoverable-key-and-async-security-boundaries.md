# 011. Восстанавливаемая смена ключа и асинхронные security-границы

Дата: 2026-10-02.

Решение: перед сменой ключей TDLib/архива сохранять атомарный `PendingKeyChange` с двумя конфигурациями и перекрёстно зашифрованными ключами. Возобновлять операцию только вперёд, к новой конфигурации. Архив проверять до присоединения; окончательные metadata записывать после replay, journal удалять только после успешного завершения.

Почему: TDLib, отдельный SQLite-архив и файл настроек не имеют общей транзакции. Ошибка checkpoint/VACUUM после SQLite commit не означает rollback. Обратная «компенсация» сама может отказать и оставить три разных ключевых состояния. Долговечный journal позволяет повторить операцию с доступным старым/новым паролем без сохранения открытого ключа или пароля.

Решение для обновлений: записи текста/правки во время владения архивом worker коалесцировать в RAM; непереигрываемые постоянные удаления/purge применять к проверенному исходному архиву либо сохранять ID в pending journal. После восстановления повторять их перед окончательными metadata. Purge терминален для Save/Edit. Нельзя завершать операцию без архива, если долговечные ID ещё ждут replay. PinLocal/Forget и добровольный уход из аккаунта/процесса до завершения запрещены.

Следствие: ключи и удаления ранее сохранённых строк переживают перезапуск при успешной записи journal; новые текстовые кэш-наблюдения в RAM могут потеряться при аварии. Не вводится второй полнотекстовый spool или обещание атомарной доставки всей истории Telegram. Maintenance после rekey/purge сообщает предупреждение, но не превращает совершившийся commit в ошибку перехода.

Решение для плагинов: вся цепочка события → очередь → действие → retry/завершение несёт `Origin { client_id, account_id }`. Ready, origin, enabled, permissions и dry-run проверяются в приложении перед эффектом и продолжением удаления, а не только внутри Lua. Account/policy/FloodWait обрабатываются перед tick через ограниченное коалесцированное управление; event/retry/output очереди ограничены. Отключение сохраняет отменяющее намерение даже при быстром повторном включении.

Почему: host и async-task переживают изменение UI/аккаунта; совпадение user ID не доказывает совпадение клиента. Удаление уже полученного события невозможно, но его исполнение можно отклонить. Управление не должно стоять за backlog сообщений.

Решение для worker: permit animation/photo переходит в поток или blocking-closure и возвращается только после фактического выхода. Отмена waiter вызывает кооперативную остановку, но не освобождает чужой работающий permit. FFmpeg interrupt callback сохраняет ограничения протоколов/форматов.

Решение для секретов: не-Copy `Key` разделяет очищаемое heap-хранилище; вывод Argon2 пишет в него непосредственно, а приложение владеет очищаемым scratch. Парольные строки используют разделяемое очищаемое владение с redacted Debug. Секретные TDLib-запросы не передаются через обычные generated String-аргументы: Rust-owned JSON и wire-буферы очищаются в границе отправки. Observer удаляет точную подписку при Drop, malformed ответы дают структурную диагностику без payload.

Отвергнутые альтернативы: обратный rekey при любой ошибке; открытые ключи/пароли в настройках; неограниченный общий канал плагинов; освобождение permit при cancel UI; определение видимости ссылки по тексту синтетической маски; отдельный String code-span на каждую строку.

Границы: это не физическое стирание SQLite/WAL/backup и не контроль копий внутри iced/TDLib/криптобиблиотек или ОС. Journal хранит открытые metadata/ID, не текст сообщения. Зависание нативной функции может удержать ограниченный permit до выхода.

Проверка: поведенческие регрессии через настоящий App/HostHandle/SQLite, standalone проверки настоящих vendored Observer/response, локальная TDLib и headless render. Конкретные команды, результаты и непроверенные случаи — в [описании исправлений](../security-fixes-2026-10-02.md).
